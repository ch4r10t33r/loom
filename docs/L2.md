# Loom as an L2: architecture note

**Status: exploratory.** This is a design study, not a roadmap commitment. It
records what "build Loom as an L2" would mean, what it would involve, and which
parts are premature. Where this note and [ROADMAP.md](ROADMAP.md) differ, the
roadmap governs status (and today the roadmap does not include any of this).

## What "L2" means here, and the recommendation

"Build Loom as an L2" can mean two different things:

1. **Loom's economic layer runs on an L2.** Provider registry, staking, and
   usage settlement live in smart contracts on an existing rollup (Base,
   Arbitrum, OP). Loom is an app; it does not run a chain.
2. **Loom is an L2.** An app-specific rollup (OP Stack / Arbitrum Orbit / ZK
   Stack / a Celestia sovereign rollup) whose state is the compute market,
   settling to Ethereum L1.

**Recommendation: pursue (1) first, not (2).** Running a rollup (sequencer, data
availability, bridge, prover, upgrade governance, liveness) is a large separate
discipline, and nothing about Loom's early needs requires it. Be an app on an L2
until throughput or custom on-chain execution forces the graduation (see
"When your own L2 is justified").

## The load-bearing principle: the chain never touches the token loop

This mirrors a rule Loom already lives by (no coding in the token loop): the
chain stays out of the inference hot path. The split:

| Off-chain (Loom's existing p2p) | On-chain (the L2) |
|---|---|
| Expert distribution, gossip, committees | Provider registry + stake |
| The actual inference | Periodic settlement of aggregated receipts |
| Signed usage receipts per request | Dispute / slashing court |
| Model weights (370 GB, never on-chain) | Model version commitment (Merkle root) + hardfork votes |

Inference produces signed receipts off-chain; the chain settles net balances
periodically and adjudicates disputes. Per-token on-chain payment is a
non-starter (too high frequency even for an L2), so the money mechanism is one of:

- **Payment / state channels:** deposit on the L2, exchange signed off-chain
  balance updates per request, settle net on channel close.
- **Optimistic aggregated receipts:** the provider accumulates signed receipts,
  submits a batch root periodically, and consumers can dispute within a window.

The L2 is the settlement and dispute court, not the per-request processor.

## The seams already in Loom

The economic layer is mostly filling in hooks that already exist:

- **Identity + signed receipts.** Metering already names "client keypair/HMAC
  identity + signed receipts" as the prerequisite. This is pure Loom work, no
  chain required, and is step 1 regardless.
- **Settlement rail.** The `credit(client, amount, proof)` op has an unverified
  `proof` field today. That field is where on-chain payment verification
  or a channel update plugs in.
- **Model-version commitment + governance.** The Merkle-rooted manifest version
  id and the "majority hardfork on a new GGUF" flow become an on-chain
  commitment and an on-chain vote.
- **Staking / slashing.** Providers stake the token; wrong bytes, unavailability,
  or failed verification slash it. This replaces the trusted-operator assumption
  and unlocks the v2 permissionless swarm.

## The hard problem is verification, not the chain

On-chain settlement is meaningless unless a provider's correct serving can be
proven. The chain part is easy. Proving correct serving is the hard part, and
it is Loom's v2 verification plane:

- **Weight integrity (cheap, already built).** The Merkle manifest proves the
  right weights were served. Anchor the root on-chain and this is free.
- **Redundant recompute + M-of-N voting (pragmatic).** Sample tokens, recompute
  on other providers, slash on mismatch. This is what makes an optimistic
  crypto-economic market work without exotic cryptography.
- **TEE attestation.** SGX / SEV / confidential-GPU attestation proves the right
  binary ran on the right weights; the attestation is verified on-chain.
- **zkML (aspirational).** A cryptographic proof of correct inference. At
  frontier-model scale the proving cost dwarfs the inference itself today. Keep
  it a stub interface, not a plan.

The realistic v1 economic layer is optimistic: signed receipts plus
crypto-economic slashing driven by redundant recompute, with weight integrity
anchored on-chain. None of that requires a custom rollup.

## Receipt to settlement to slashing (the flow)

```
consumer/light node                provider/full node                 L2 contracts
       |                                   |                                |
       |-- request (signed) -------------->|                                |
       |<-- response + signed receipt -----|  (off-chain, hot path)         |
       |                                   |                                |
       |          ... many requests, receipts accumulate ...                |
       |                                   |                                |
       |                                   |-- submit aggregated receipts -->| settle net,
       |                                   |   (batch root, periodic)        | move escrow
       |                                   |                                |
   verifier (sampled recompute) --- mismatch? --> submit fraud proof ------->| slash stake
```

## A phased path

1. **Signed receipts + identity (no chain).** Provider/consumer keypairs; every
   metered response is a signed receipt. Prerequisite regardless.
2. **Contracts on an existing L2** (Base/Arbitrum/OP): provider registry,
   staking, a settlement contract that accepts aggregated signed receipts with a
   dispute window; payment channels for micropayments. No own-chain.
3. **Verification to slashing oracle.** Wire v2 redundant-recompute / TEE
   attestation to the on-chain slasher. This is where the real engineering and
   risk sit.
4. **Token + rewards** if warranted: emissions for serving hot experts and
   holding cold-tier durability shards, fee capture. Regulatory exposure
   (securities, money transmission) becomes real and costly here.
5. **Graduate to your own L2 only when justified** (below).

## When your own L2 is justified

The reasons to run a rollup are throughput and custom execution:

- You want the verification/settlement logic to be the chain's native execution.
- You need cheaper or denser data availability for receipts at scale
  (EigenDA / Celestia).
- You want sovereign governance over the model-version state.

Until one of those bites, contracts on an existing L2 plus channels give a
trustless-enough market without a sequencer.

## What to push back on

- **Do not build your own L2 to start.** It is expensive and answers a
  question Loom does not have yet.
- **Sequence economics after utility.** The classic DePIN failure is shipping a
  token economy before the technical thesis (distributed frontier-MoE serving is
  useful and fast enough) is proven. A token does not fix a weak answer to that
  question.
- **The moat is the verification story, not the chain.** Anyone can deploy
  staking contracts. Whether Loom can cheaply prove correct MoE inference is the
  real differentiator and the main research risk.
